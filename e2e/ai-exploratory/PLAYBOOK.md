# AI 探索测试手册（Kimi WebBridge）

> 用途：任何 AI 代理（或人类）按本手册对系统执行**探索性测试**——不是跑固定脚本，
> 而是基于对系统的理解主动寻找 bug。
> 运行环境：本地 dev（5173+8080）+ WebBridge daemon + 测试账号 e2e_test。

## 0. 必读上下文（先读这些再动手）

1. `e2e/ai-exploratory/PROJECT-KNOWLEDGE.md` —— 业务规则、状态模型、数据红线
2. `e2e/ai-exploratory/RISK-LEDGER.md` —— 风险台账（优先验证 🔍 状态的条目）
3. `e2e/README.md` —— 测试账号、服务地址、已有回归覆盖（不要重复测）

## 1. 探索策略（按 bug 家族主动出击）

### 策略 A：状态同步审计
对系统中"同一事实的多个状态源"做排列组合，制造它们的不同步：
- 删除 X 后，检查所有展示 X 的地方：下拉框、URL 参数、本地草稿、通知、演示模式、提交管理、导出、AI 分析的输入
- 修改 X 后，检查所有缓存 X 的地方是否刷新

### 策略 B：时间边界攻击
- 把测试周期 deadline 设为 1 分钟后，等到过期，继续编辑看系统行为
- 周末/深夜操作（当前周计算在周五切换）
- 修改系统时区后操作

### 策略 C：并发踩踏
- 开两个标签页登录同一账号，同时编辑同一周报的同一字段，检查合并/冲突处理
- A 标签页编辑时，B 标签页删除该周期

### 策略 D：输入混沌
- 整段解析：喂真实历史周报原文（从 data/周报 找）、空文本、纯序号、超长文本、emoji、中英文混合序号
- Excel 导入：缺列、多空格、合并单元格

## 2. 执行循环

```
1. 从 RISK-LEDGER 选一条 🔍 风险（或自己推理一条新风险）
2. 写下假设：「如果 <条件>，系统会 <错误行为>，因为 <推理链>」
3. 用 WebBridge 构造场景（导航/点击/注入/读页面）
4. 判定：
   - 复现 → 🐞 记录为确认 bug：最小复现步骤 + 截图 + 推理链
   - 未复现 → 检查代码确认防护逻辑 → 标记 ❌（误报）并写明防护在哪
5. 更新 RISK-LEDGER 状态
6. 确认 bug → 修复后必须沉淀为 e2e/tests/ 下的确定性回归用例
```

## 3. 输出格式（每次探索结束交付）

```markdown
## 探索报告 <日期>
### 验证的风险
| 风险 | 假设 | 结果 | 证据 |
### 新发现的 bug（含最小复现）
### 误报清单（防护逻辑位置）
### 沉淀的回归用例
### 建议（设计层面）
```

## 4. 纪律

1. 不碰真实数据（红线见 PROJECT-KNOWLEDGE 第 5 节）
2. 每个 bug 必须有最小复现，不接受"好像有问题"
3. 误报也是成果：它证明了防护存在，必须记录防护位置防止后人重复怀疑
4. 确认 bug 不过夜转化为回归用例，否则同样的问题会被"发现"两次
