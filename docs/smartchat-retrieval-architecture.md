## 一、当前架构现状

### 1.1 SmartChat 检索链路

当前 SmartChat 的复杂查询走以下链路：

```
用户自然语言 query
    ↓
硬编码关键词 if/else 路由（SmartChat.tsx 中 20+ 个条件分支）
    ↓
前端内存数组 filter + sort（O(n) 或 O(n log n)）
    ↓
结果文本化后拼入 LLM prompt
    ↓
DeepSeek API 生成回答
```

### 1.2 现有检索函数

| 函数 | 数据源 | 能力 |
|------|--------|------|
| `retrieveEmployeeWideTable()` | `employee-wide-table.json` | 宽表字段匹配、数值排序、部门过滤 |
| `retrieveEmployeeByRules()` | `employee-wide-table.json` | 数值标准化 + 加权评分 |
| `retrieveEmployeeByTags()` | `employee-tags.json` | 同义词映射 → 标准标签 → AND-OR 复合筛选 |
| `executeSQL()` | `employee-wide-table.json` | **仅 DatabasePage 使用**，前端伪 SQL 引擎 |

### 1.3 当前关键缺陷

| 缺陷 | 影响 |
|------|------|
| **条件无法组合** | "考试成绩最高 + 加班最多 + AI经验" 被拆成 3 条独立查询，无法做交集 |
| **权重无法表达** | 用户说"优先看考试成绩，代码量参考" → 当前只能字典序排序 |
| **语义丢失** | "AI 开发经验" = `includes('AI算法与大模型')`，漏掉"深度学习"、"TensorFlow"等 |
| **性能瓶颈** | 全量 JSON（203人 × 82字段 ≈ 1.2MB）加载到前端内存，数据量增大后卡死 |
| **LLM 幻觉风险** | 检索结果为空时，LLM 容易编造数据 |

## 二、核心问题定义

### 2.1 典型复杂查询示例

> **"找工作时间最长、考试成绩最高、且有 AI 开发经验的十个人"**

拆解：
- **数值型条件 A**：`平均加班时长` → 降序排序
- **数值型条件 B**：`考试成绩` → 降序排序
- **非数值型语义条件**：`有 AI 开发经验` → 不是数据库字段，是语义概念
- **数量限制**：Top 10

### 2.2 为什么当前代码处理不了

当前代码的做法：
```javascript
if (q.includes('工时') || q.includes('加班')) {
  // 只返回加班最多的人，不管考试成绩和 AI 经验
  return 日均工时TopN;
}
if (q.includes('考试')) {
  // 只返回考试成绩最高的人，不管加班和 AI 经验
  return 考试成绩Top5;
}
```

**三个条件各自为政，never 被组合执行。**

## 三、最优架构设计：Query-Retrieve-Generate 三阶段管道

### 3.1 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  SmartChat.tsx（前端，只负责 UI + 调用 API）                  │
│  用户输入 → 调用 /api/chat/search → 接收结构化结果 → 展示    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  后端服务：Query-Retrieve-Generate 管道                      │
│                                                              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  ① Query    │→│ ② Retrieve  │→│ ③ Generate  │         │
│  │   理解层     │  │   检索层     │  │   生成层     │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 ① Query 理解层（Intent Parsing）

**目标**：把自然语言转成机器能执行的结构化查询计划（QueryPlan）。

**输入**：
> "工作时间最长、考试成绩最高、且有 AI 开发经验的十个人"

**输出**（JSON Schema）：
```json
{
  "intent": "employee_search",
  "filters": [
    {"field": "平均加班时长", "op": ">", "value": 0},
    {"field": "考试成绩", "op": ">", "value": 0}
  ],
  "semantic_conditions": [
    {
      "concept": "AI开发经验",
      "fields": ["技术方向", "summary", "标签体系", "现在的工作岗位"],
      "weight": 0.2
    }
  ],
  "sort": [
    {"field": "平均加班时长", "order": "desc", "weight": 0.4},
    {"field": "考试成绩", "order": "desc", "weight": 0.4}
  ],
  "limit": 10,
  "output_fields": ["姓名", "团队", "现在的工作岗位", "平均加班时长", "考试成绩", "技术方向"]
}
```

**实现方式**：

| 方案 | 原理 | 优缺点 | 适用阶段 |
|-----|------|--------|---------|
| **LLM 函数调用** | GPT-4/DeepSeek/通义千问输出结构化 JSON | 准、覆盖全、慢、贵 | 生产环境 |
| **规则模板 + BERT** | 小模型做意图分类，正则提取字段 | 快、便宜、覆盖有限 | 中期过渡 |
| **硬编码升级** | 正则/关键词提取字段、权重、数量 | 最快实现、维护地狱 | Demo 阶段 |

**关键理解**：LLM 不只是"翻译字段名"，还要理解：
- 这是**排序**还是**过滤**？
- 数值条件的**权重**是多少？
- "AI 开发经验"是**语义概念**，不是数据库字段

### 3.3 ② Retrieve 检索层（核心）

**目标**：根据 QueryPlan 执行高效、准确的混合检索。

**分层漏斗**：

```
第 1 层：数据库索引过滤（毫秒级）
   WHERE 平均加班时长 IS NOT NULL AND 考试成绩 IS NOT NULL
   → 10万人 缩小到 ~8万人

第 2 层：向量语义检索（百毫秒级）
   找和"AI开发经验"向量最相似的 Top 200
   → 与第 1 层取交集 = ~150人

第 3 层：加权融合排序（毫秒级）
   score = 0.4 × norm(加班) + 0.4 × norm(考试) + 0.2 × sim(AI)
   → 输出 Top 10
```

**为什么必须分层**：
- 如果先做向量检索（10万人里跑）→ 太慢
- 如果先做数据库过滤 → 毫秒级缩小候选集，向量检索只在少量数据上跑

### 3.4 ③ Generate 生成层

**目标**：LLM 只负责"格式化输出"，不负责"找数据"。

**给 LLM 的 prompt 结构**：
```
你是智能人力资源助手。以下是检索系统已经计算好的结果，请直接引用：

【检索结果】
排名 | 姓名 | 团队 | 岗位 | 加班时长 | 考试成绩 | AI经验匹配度 | 综合得分
1    | 张三 | 数据平台部 | 算法工程师 | 45h | 92分 | 0.95 | 0.91
2    | 李四 | 智能平台部 | AI工程师 | 42h | 88分 | 0.92 | 0.87
...

请直接给出Top10名单，说明推荐理由。禁止编造不在列表中的人。
```

**好处**：
- ✅ LLM 不会幻觉（数据是检索层给的）
- ✅ LLM 不会排序错误（排序是检索层算的）
- ✅ 输出格式精确可控

## 四、数值型检索 vs 非数值型语义检索

### 4.1 对比表

| 维度 | 数值型检索 | 非数值型语义检索 |
|------|-----------|----------------|
| **示例字段** | 考试成绩、加班时长、代码量、工龄 | summary、技术方向、项目经历、评价文字 |
| **用户 query 示例** | "考试成绩最高的"、"加班超过40小时的" | "有AI开发经验的"、"擅长数据治理的" |
| **检索方式** | 数据库索引 + ORDER BY / WHERE | 向量 Embedding + 余弦相似度 |
| **评分范围** | 原始数值（需归一化到 0~1） | 余弦相似度（天然 0~1） |
| **生产工具** | PostgreSQL B-tree 索引 / ClickHouse | pgvector / Milvus / Elasticsearch |
| **当前代码做法** | JS `filter()` + `sort()` | `includes()` 子串匹配 |

### 4.2 为什么非数值型不能用数据库 LIKE

假设数据库有字段 `技术方向`：

| 员工 | 技术方向 | `LIKE '%AI%'` | 向量语义匹配"AI开发经验" |
|------|---------|--------------|------------------------|
| A | AI算法与大模型 | ✅ 命中 | 0.95 |
| B | 深度学习 | ❌ 漏掉 | 0.88 |
| C | TensorFlow模型部署 | ❌ 漏掉 | 0.82 |
| D | 数据治理与合规 | ❌ 不命中 | 0.15 |

**结论**：`LIKE` 只能做字面匹配，向量语义匹配能理解概念关联。

## 五、向量语义检索详解

### 5.1 原理

将文本转换为高维向量（通常 768~1536 维），通过**余弦相似度**计算语义相近程度：

```
cos(θ) = (A · B) / (|A| × |B|)
```

### 5.2 分数含义

| 余弦相似度 | 含义 |
|-----------|------|
| 0.90 ~ 1.00 | 几乎同义（"AI开发" vs "人工智能开发"） |
| 0.70 ~ 0.90 | 强相关（"AI开发" vs "深度学习"） |
| 0.40 ~ 0.70 | 弱相关（"AI开发" vs "数据分析"） |
| 0.00 ~ 0.40 | 基本不相关（"AI开发" vs "行政专员"） |

### 5.3 预处理流程

```
员工文本 = 姓名 + 团队 + 岗位 + 技术方向 + summary + 标签体系
         ↓
    Embedding 模型（如 BGE-M3）
         ↓
    1024维向量 → 存入向量数据库
```

### 5.4 查询流程

```
用户 query: "AI开发经验"
         ↓
    同一模型生成 query 向量
         ↓
    向量数据库检索 Top K
         ↓
    返回: [(员工ID, 相似度分数), ...]
```

### 5.5 Embedding 模型选型

| 模型 | 语言 | 维度 | 特点 | 成本 |
|------|------|------|------|------|
| **BGE-M3** | 多语言 | 1024 | 开源、中文强、支持长文本 | 免费 |
| **text-embedding-3** | 多语言 | 1536 | OpenAI、效果顶尖 | 按量计费 |
| **通义千问 Embedding** | 中文 | 1536 | 阿里云、中文场景优化 | 按量计费 |

**推荐**：Demo/中期用 BGE-M3（免费、效果够用），生产环境可升级到 text-embedding-3。

## 六、加权融合排序

### 6.1 为什么需要归一化

不同字段量纲不同，不能直接相加：

| 字段 | 范围 | 不归一化的后果 |
|------|------|--------------|
| 考试成绩 | 0 ~ 100 | 被代码量完全压制 |
| 加班时长 | 0 ~ 100 小时 | 被代码量完全压制 |
| 代码量 | 0 ~ 30,000,000 行 | 一个字段决定排序 |

### 6.2 Min-Max 归一化公式

```
norm(x) = (x - min) / (max - min)
```

归一化后所有字段都在 0~1 范围内，可以公平比较。

### 6.3 融合公式

```javascript
综合分 = w₁ × norm(字段A) + w₂ × norm(字段B) + w₃ × 语义相似度
```

**示例**：
```javascript
score = 0.4 × norm(平均加班时长) 
      + 0.4 × norm(考试成绩) 
      + 0.2 × sim(AI开发经验)
```

### 6.4 动态权重策略

根据用户 query 的措辞自动调整权重：

| 用户措辞 | 权重调整 |
|---------|---------|
| "优先看考试成绩" | 考试成绩 weight ↑ |
| "代码量参考一下" | 代码量 weight ↓ |
| "能力最强" | 语义匹配 weight ↑ |
| "综合排名" | 均匀分布 |

## 七、渐进式演进路径

### 7.1 阶段划分

| 阶段 | 数据量 | 数值检索 | 语义检索 | 架构改动 |
|-----|--------|---------|---------|---------|
| **现在（Demo）** | 200人 | JS `filter`+`sort` | `includes()` 子串匹配 | 0 |
| **阶段一** | <5,000人 | PostgreSQL + 复合索引 | pgvector / ES 全文检索 | 中加后端接口 |
| **阶段二** | <50,000人 | PostgreSQL + 物化视图 | pgvector + 预计算 Embedding | 中加向量表 |
| **阶段三** | >100,000人 | ClickHouse 列式存储 | Milvus 独立集群 + 缓存 | 高架构拆分 |

### 7.2 阶段一最小可行方案（推荐下一步）

**不改前端架构，只改后端**：

1. **数据迁移**：CSV → PostgreSQL
2. **建复合索引**：`(考试成绩, 平均加班时长, 提交代码量)`
3. **加向量字段**：`employee_embeddings` 表（id, employee_id, embedding vector(1024)）
4. **后端接口**：`/api/chat/search`
   ```json
   // 请求
   {"query": "考试成绩最高且会AI的10个人"}
   
   // 响应
   {"results": [...], "scores": [...]}
   ```
5. **SmartChat 改造**：删除前端检索逻辑，改为调后端接口

### 7.3 Demo 阶段的最小过渡方案（现在就能做）

如果暂时不想动后端，可以在前端先做"伪语义匹配"过渡：

```javascript
// 第 1 步：规则提取 QueryPlan
const plan = {
  numericSort: [
    {field: '考试成绩', weight: 0.4},
    {field: '平均加班时长', weight: 0.4}
  ],
  semanticKeywords: ['AI', '算法', '大模型', '深度学习', 'TensorFlow'],
  limit: 10
};

// 第 2 步：关键词扩展做"伪语义匹配"
const semanticScore = (employee) => {
  const text = (employee['技术方向'] || '') + (employee['summary'] || '');
  let score = 0;
  for (const kw of plan.semanticKeywords) {
    if (text.includes(kw)) score += 0.25;
  }
  return Math.min(score, 1);
};

// 第 3 步：加权融合排序
const normalize = (arr, field) => {
  const vals = arr.map(e => parseFloat(e[field]) || 0);
  const min = Math.min(...vals), max = Math.max(...vals);
  return (val) => max === min ? 0 : (val - min) / (max - min);
};

employees.sort((a, b) => {
  const norm = normalize(employees, '考试成绩'); // 同理加班时长
  const scoreA = 0.4 * norm(a['考试成绩']) + 0.4 * norm(a['平均加班时长']) + 0.2 * semanticScore(a);
  const scoreB = 0.4 * norm(b['考试成绩']) + 0.4 * norm(b['平均加班时长']) + 0.2 * semanticScore(b);
  return scoreB - scoreA;
});
```

**局限性**：只能处理预定义的同义词，无法真正理解语义。数据量超过 5,000 人后必须后端化。

## 附录：当前代码对照表

| 步骤 | 最优架构 | 当前代码实际做的 | 差距 |
|-----|---------|----------------|------|
| **Query 理解** | LLM/模型解析成结构化 QueryPlan | 硬编码 `if/else` 关键词匹配 | 无法处理组合条件、权重、语义 |
| **数值型检索** | 数据库索引 `ORDER BY` / `WHERE` | JS 数组 `filter()` + `sort()` | O(n log n) 全量内存排序 |
| **非数值型检索** | 向量 Embedding 余弦相似度 | `includes()` 子串包含 | 漏掉同义词、无法理解语义 |
| **多条件融合** | 归一化后加权公式算综合分 | 字典序逐字段比较 | 无法表达权重差异 |
| **Top N 截取** | `LIMIT 10` | `slice(0, 10)` | 功能相同，但前端大数据量卡死 |
| **结果生成** | LLM 只负责格式化（数据已排好） | LLM 接收文本后自己理解归纳 | LLM 容易幻觉、排序错误 |
