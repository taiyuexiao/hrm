# 可能影响系统稳定运行的风险（大白话版）

> 本文档把审计中**可能导致系统跑不起来、权限乱掉、数据丢失或功能异常**的条目单独挑出来，用大白话再讲一遍。

---

## 一、最要命：服务器数据库里的角色字段没改对

### 什么意思

咱们这次重构把权限模型从「硬编码工号」改成了「数据库 role 字段」。代码已经按新模型跑了，但**生产服务器上的 SQLite 数据库 `hr.db` 里，用户的 `role` 字段可能还是旧值**。

### 当前正确的角色应该是

| 用户名 | 姓名 | 正确角色 | 旧角色可能是什么 |
|---|---|---|---|
| 306852 | 于浩瀚 | `leader`（总经理室） | 之前是 `admin` |
| 314043 | 宋晓迪 | `leader`（总经理室） | 之前是 `admin` |
| 301953 | 徐启鹏 | `leader`（总经理室） | 之前是 `admin` |
| 306776 | 卢易 | `leader`（总经理室） | 之前是 `admin` |
| 319915 | 马胤 | `admin`（管理员） | 之前是 `user` |
| 303423 | 许阿云 | `admin`（管理员） | 之前就是 `admin` |
| 33528 | 管理员 | `superadmin`（超级管理员） | 之前是 `admin` |

### 如果服务器 DB 没改，会发生什么

1. **4 位总经理室成员会变成「管理员」**
   - 他们能编辑所有科室、所有周次的周报。
   - 他们能删除周报周期、解锁/锁定周报、删除别人的评论。
   - 这完全违背你设计的「总经理室只能看、不能编辑」的规则。

2. **33528 不再是「超级管理员」**
   - 虽然代码里 `33528` 有兜底超管逻辑，但如果某处判断依赖 `role == 'superadmin'`，可能出意外。
   - 最直观的是：权限管理界面可能不显示「超级管理员」标签，角色下拉也选不到 `superadmin`。

3. **319915 名义上不是管理员**
   - 代码里我留了硬编码 fallback：`319915` 仍会被识别为管理员。
   - 所以即使 DB 没改，他也能用管理员功能；但这是一个「偷偷生效」的状态，和 DB 里显示的不一样，容易让管理员产生困惑。

### 部署前必须执行

```sql
UPDATE users SET role = 'leader' WHERE username IN ('306852','314043','301953','306776');
UPDATE users SET role = 'admin'  WHERE username IN ('404423','319915','303423');
UPDATE users SET role = 'superadmin' WHERE username = '33528';
```

执行后建议再查一遍确认：

```sql
SELECT username, name, role FROM users
WHERE username IN ('306852','314043','301953','306776','319915','303423','33528');
```

## 二、有人能一键清空所有周报数据

### 什么意思

后端有一个接口 `DELETE /api/reports`，作用是清空 `weekly_reports` 表。这个接口**没有任何登录、权限检查**。

### 会发生什么

- 任何人（包括没登录的人）只要能访问到内网地址，发一个 HTTP 请求，所有周报记录就没了。
- 前端目前没有「清空全部」按钮，但接口是公开的，不依赖前端。

### 影响

- **数据全部丢失**，系统直接变空壳。
- 如果有备份还能恢复，但业务会中断。

## 三、普通用户能为任意科室创建周报

### 什么意思

保存周报的接口 `POST /api/reports` 在「周报已经存在」时会检查权限，但在「周报不存在」时直接创建新记录，**不检查用户有没有权限、是不是该科室的人**。

### 会发生什么

- 普通用户可以为「数据开发部」「智能平台部」等他不在的科室创建周报。
- 可以为过去的任意历史周次、未来的任意周次创建周报。
- 导入功能也会触发这个缺口：导入 Excel 时会自动为不存在的科室创建报告。

### 影响

- 周报数据里会出现大量「不应该存在的记录」。
- 科室负责人发现自己科室多了不是他填的周报。
- 你设计的「只能编辑本周、只能编辑自己科室」规则被绕过。

## 四、改密码接口不需要登录

### 什么意思

`POST /api/auth/change-password` 只要知道旧密码就能改，**不需要先登录，也不要求只能改自己的密码**。

### 会发生什么

- 只要猜出或知道一个人的旧密码，就能把他的密码改成别的。
- 未登录者也可以不断尝试调用这个接口。

### 影响

- 账号被盗用。
- 如果 33528 的密码被猜到，整个系统被接管。

---

## 五、Spring Security 默认放行所有请求

### 什么意思

后端的 Spring Security 配置是 `anyRequest().permitAll()`，意思是「所有请求默认都允许访问」。权限检查全靠每个 Controller 自己写代码判断。

### 会发生什么

- 如果某个 Controller 忘了写权限判断，这个接口就是公开的。
- 实际上已经发生：清空周报、读取周报、AI 解析、新建周报等接口都因此暴露。

### 影响

- 这是「安全兜底」失效。
- 即使以后加新接口，也很容易因为忘记写权限检查而暴露。

## 六、JWT 密钥是硬编码的弱密钥

### 什么意思

系统用 JWT Token 做登录凭证签发。签发 Token 需要一个密钥。当前配置文件里的密钥是：

```yaml
jwt.secret: ${JWT_SECRET:intelligent-hr-system-secret-key}
```

如果生产环境没有设置 `JWT_SECRET` 环境变量，就会用 fallback 的 `intelligent-hr-system-secret-key`。

### 会发生什么

- 任何人拿到这个密钥，就能伪造 33528 的 Token。
- 拿着伪造 Token 调接口，系统会认为是真管理员。

### 影响

- **整个权限体系失效**，所有「仅超管可操作」的接口都能被冒用。
- 部署配置 `deploy-config/application.yml` 里还写了 `JWT_SECRET: CHANGE_THIS_IN_PRODUCTION`，如果运维没改就直接用，同样危险。

## 七、未登录就能读取全部周报

### 什么意思

`GET /api/reports`（查所有周报）和 `GET /api/reports/{weekLabel}/{dept}`（查单篇周报）**不需要登录**。

### 会发生什么

- 任何人只要能访问内网地址，就能看到所有科室的周报内容、评论、提交记录。
- 即使前端菜单隐藏了，直接调接口也能拿到。

### 影响

- 敏感工作内容泄露。
- 与「登录后才能查看周报」的预期不符。

## 八、未登录就能调用 AI 解析

### 什么意思

`POST /api/ai/parse-text` 不需要登录，把文本发过去，后端会调 LLM。

### 会发生什么

- 任何人都能调用，产生 LLM 费用。
- 可能把内部敏感文本发到 LLM。

### 影响

- 成本失控。
- 数据外泄风险。

## 九、评论/回复可以冒充别人发

### 什么意思

发评论、回复时，前端会把 `authorId`（作者工号）传给后端，但后端**不检查这个 `authorId` 是不是真的属于当前登录用户**。

### 会发生什么

- 用户 A 登录后，可以构造请求，把 `authorId` 写成用户 B，发一条「B 的评论」。
- 后续「作者可以删自己评论」的逻辑也依赖这个 `authorId`，所以判断基础是不可靠的。

### 影响

- 评论来源不可信。
- 可能出现恶意冒充、伪造审批意见等情况。

## 十、前端路由没有守卫，输 URL 就能进管理页

### 什么意思

前端只是在菜单和按钮上做隐藏（比如没权限就不显示「权限管理」按钮），但**路由层面没有拦截**。

### 会发生什么

- 普通用户直接浏览器输入 `http://前端地址/#/admin/permissions` 就能打开权限管理页面。
- 输入 `/admin/action-logs` 能打开行为日志页面。
- 输入 `/knowledge-base` 能打开知识库页面。

### 影响

- 虽然后端接口多数会拒绝执行，但页面能打开，信息可能泄露。
- 用户体验和安全感都不好。

## 十一、前端权限状态存在 localStorage 里，改后不会自动刷新

### 什么意思

用户登录后，前端把角色、权限列表存在浏览器 `localStorage` 的 `auth-user` 里。之后菜单、按钮都读这个缓存。

### 会发生什么

- 管理员在后台把用户 A 从「普通用户」改成「管理员」，用户 A 不重新登录，界面还是按旧角色显示。
- 用户 A 甚至可以手动改 `localStorage` 里的 `role` 和 `permissions`，让自己看到更多菜单。

### 影响

- 界面显示和实际权限不同步。
- 虽然后端接口会拦下非法操作，但容易让人困惑，也不美观。

---

## 十二、改角色会清空之前单独授予的特殊权限

### 什么意思

后端 `PUT /api/auth/users/{username}` 改角色时，会把该用户的 `permissions` JSON 重置为角色默认权限。

### 会发生什么

- 假设你给某普通用户单独开了「编辑历史周报」权限（`EDIT_HISTORY`）。
- 后来因为这人调岗，管理员把他的角色从 `user` 改成 `admin`。
- 改完后，他确实有了管理员默认权限，但之前单独授予的 `EDIT_HISTORY` 会被清空（虽然 admin 本来也有这个权限，但逻辑上是覆盖）。
- 如果是 `admin` 改 `leader`，原来单独授予的权限也会丢失。

### 影响

- 特殊授权在角色变更后丢失，需要重新手动配置。
- 管理员可能没意识到这一点。

## 十三、硬编码 fallback 工号会让某些账号「删不掉权限」

### 什么意思

代码里保留了旧管理员工号（404423/319915/303423）和旧领导工号（306852/314043/301953/306776）作为 fallback。

### 会发生什么

- 假设你想把 `319915` 的管理员权限取消，在 DB 里把他的 `role` 改成 `user`。
- 但代码 fallback 会把他仍然识别为管理员，权限没真正取消。
- 反过来，如果某个新用户工号恰好是 `404423`（这个工号目前不在系统里），他会被自动当成管理员。

### 影响

- 权限调整可能不生效。
- 存在意外提权风险。

## 十四、部署包里带了旧数据库备份

### 什么意思

`deploy-package/data/hr.db.bak.20260625202004` 是一个旧的数据库备份文件，里面的角色字段还没迁移。

### 会发生什么

- 如果运维部署时误把这个备份重命名成 `hr.db`，或者直接用它恢复数据，上线的就是错误角色状态。
- 4 位总经理室成员又变成管理员。

### 影响

- 等同于「服务器 DB 角色没迁移」的风险。
- 备份文件随压缩包分发，增加误操作概率。

## 十五、前后端分离部署时，前端找不到后端

### 什么意思

`deploy-package/dist/app-config.json` 里写的是：

```json
{"apiBaseUrl":"/api"}
```

这表示前端会调用「当前域名下的 `/api`」。

### 会发生什么

- 如果前端和后端部署在同一个域名、用 Nginx 反代，这个配置能用。
- 如果前后端分开部署（前端一个地址，后端一个地址），前端请求 `/api` 会 404，或者因跨域被浏览器拦住。

### 影响

- 页面能打开，但所有数据都加载不出来，系统无法使用。
- 部署前需要根据实际架构改成类似 `http://后端IP:8080/api`。

## 十六、LLM API Key 明文写在配置文件里

### 什么意思

`deploy-config/application.yml`、`deploy-package/config/application.yml`、`docs/project-docs/DEPLOY.md` 里都明文写了 LLM 的 API Key。

### 会发生什么

- `deploy-package.zip` 一旦外传，Key 就泄露。
- 拿到 Key 的人可以在外面调用你们的 LLM 服务，产生费用或滥用。

### 影响

- 密钥泄露。
- 费用与安全风险。

## 十七、新数据库初始化后，管理员左侧菜单可能缺项

### 什么意思

`users.json` 里没有 `permissions` 字段。如果生产是一套全新数据库，启动时会从 `users.json` 初始化用户，所有人的 `permissions` 都是空数组 `[]`。

前端侧边栏判断显示时，直接读 `authUser.permissions`：

- 知识库 → 需要 `KNOWLEDGE_BASE`
- 周报提交管理 → 需要 `VIEW_SUBMISSIONS`
- 行为日志 → 需要 `VIEW_ACTION_LOGS`
- 账号/权限管理 → 需要 `USER_MANAGE`/`PERMISSION_MANAGE`

### 会发生什么

- 即使 33528 是超管，他的 `permissions` 也是空的，菜单里可能不显示这些入口。
- 功能本身还能用（后端按角色授权），但用户找不到入口。

### 影响

- 新环境首次部署时，界面看起来「功能少了」。
- 需要重新登录或刷新权限缓存才能正常显示。

## 总结：哪些最可能在生产上直接让系统「跑不正常」

| 风险 | 表现形式 |
|---|---|
| 服务器 DB 角色没迁移 | 总经理室能编辑周报、权限混乱 |
| `DELETE /api/reports` 无鉴权 | 数据被一键清空 |
| `POST /api/reports` 新建无鉴权 | 出现大量不该有的周报 |
| `app-config.json` 没按部署方式改 | 前端加载不出数据 |
| JWT 密钥未改 | 任何人可冒充管理员 |
| 部署包带旧 DB 备份 | 误恢复后权限回到旧状态 |
| 新 DB 初始化后菜单缺失 | 管理员看不到管理入口 |
