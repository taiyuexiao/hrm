## 2026-07-16

### 周报操作撤销功能设计（理论方案）

- **状态**：待实现 / 理论设计阶段
- **背景**：
  - 2026-07-16 13:45:10（北京时间），管理员账号对 `20260626-综合管理部` 周报执行了一次 `edit` 操作，导致该报告的 `nextPlan` 被清空、`currentWork`/`content` 被改写。
  - 事后通过 `user_action_logs` 可定位到操作人和操作时间，但现有日志仅记录变更摘要，未保存完整数据快照，因此无法一键回退到操作前的状态。
- **核心思路**：
  - 在每次会修改周报数据的操作（`edit`、`submit`、`import_excel`、`admin_unlock`、`admin_lock` 等）执行前后，保存完整数据快照。
  - 超级管理员 `33528` 可在行为日志页面查看历史操作，并选择某条日志执行撤销。
  - 撤销时，用日志中的 `before_snapshot` 覆盖当前报告，使数据回退到操作前版本。
- **数据模型扩展**：
  - 扩展 `user_action_logs` 表，新增两个字段：
    - `before_snapshot TEXT`：操作前该周报的完整 JSON 快照
    - `after_snapshot TEXT`：操作后该周报的完整 JSON 快照（可选，用于审计比对）
  - 示例 SQL：
    ```sql
    ALTER TABLE user_action_logs ADD COLUMN before_snapshot TEXT;
    ALTER TABLE user_action_logs ADD COLUMN after_snapshot TEXT;
    ```
- **撤销流程**：
  1. 超级管理员在行为日志页面点击某条日志的「撤销」按钮。
  2. 后端校验当前用户角色为 `superadmin`（`33528`）。
  3. 读取该日志的 `before_snapshot`。
  4. 检查当前报告的 `updated_at` 是否与日志 `after_snapshot.updated_at` 一致：
     - 一致：说明日志记录后未被其他人修改，可以安全撤销。
     - 不一致：说明已有后续修改，提示用户"数据已被后续操作覆盖，无法直接撤销"。
  5. 用 `before_snapshot` 覆盖当前 `weekly_reports` 记录。
  6. 新增一条 `action='undo'` 的行为日志，记录被撤销的日志 ID。
- **权限控制**：
  - 仅超级管理员 `33528` 可查看「撤销」入口并执行撤销。
  - 在 `ActionLogPage` 中为支持撤销的操作类型显示「撤销」按钮。
  - `undo` 类型的日志本身不可再被撤销，避免无限撤销链。
- **支持撤销的操作类型**：
  - `edit`：最常见，可直接撤销。
  - `submit`：可撤销内容变更，但需单独考虑 `submissions` 提交历史链。
  - `import_excel`：一次导入可能修改多个部门，撤销时可选择"撤销单个部门"或"撤销本次导入的所有部门"。
  - `admin_unlock` / `admin_lock`：状态回退简单。
  - `delete_week`：删除整个周次，撤销需恢复该周次下所有部门报告。
  - `undo`：自身不可撤销。
- **边界情况与风险**：
  1. **并发修改**：若日志记录后报告又被他人修改，直接撤销会覆盖后续修改，必须通过 `updated_at` 校验拦截。
  2. **import_excel 批量操作**：一次导入影响多个部门，需支持批量撤销或按部门单独撤销。
  3. **提交历史**：`submit` 操作会在 `submissions` 中追加快照。撤销 `edit` 不应影响 `submissions`；撤销 `submit` 才需要处理提交链。
  4. **数据库直接修改**：通过 SQL / 脚本直接修改数据库的操作不会被日志记录，因此无法撤销。
  5. **存储空间**：每个操作保存两份完整报告快照，数据量会增长。可优化为只存 `before_snapshot`，或对大 JSON 做压缩存储。
- **实现步骤（后续开发参考）**：
  1. 修改 `user_action_logs` 表结构，新增 `before_snapshot`、`after_snapshot` 字段。
  2. 在 `ReportController.saveReport`、`submitReport`、`setUnlock`、`setLock` 等方法中，操作前后保存快照。
  3. 在导入功能 `ImportReportsModal` / `ReportController` 批量保存逻辑中，为每个受影响的部门保存快照。
  4. 后端新增 `POST /api/reports/{weekLabel}/{dept}/undo/{logId}` 接口。
  5. 前端 `ActionLogPage` 增加撤销按钮、确认弹窗、撤销结果提示。

### 修复根任务框末尾无法输入空格/回车

- **问题**：根任务框在编辑时，评论高亮覆盖层（`data-overlay`）覆盖在 `TextArea` 上方，虽然整体设置了 `pointerEvents: none`，但内部高亮 `mark` 元素设置了 `pointerEvents: auto`。当光标位于文本末尾、且存在评论高亮时，键盘事件可能被覆盖层干扰，导致空格/回车无法正常输入。
- **修复**：在 `TaskTree` 组件中新增 `editingId` 状态，当某个任务框获得焦点（`onFocus`）时临时隐藏该框的评论高亮覆盖层，失去焦点（`onBlur`）后恢复显示。这样编辑时 `TextArea` 完全不受 overlay 干扰。
- **涉及文件**：
  - `src/components/weekly-report-v2/TaskTree.tsx`
- **影响范围**：
  - 仅影响编辑状态下的高亮显示，不影响评论数据、不影响保存、不影响非编辑状态的高亮交互。
  - `PresentationView.tsx` 复用同一组件，同步修复。
- **验证**：
  - TypeScript 检查通过，前端构建成功，`deploy-package.zip` 已更新。

### 后端兜底解析任务粘贴文本（设计阶段，暂不实施）

- **背景**：
  - 当前根任务框的子任务解析完全依赖前端 `TaskTree.tsx` 中的 `parseTaskHierarchy` 正则解析，要求用户严格按换行 + `1./（1）/1）` 格式填写。
  - 实际工作中，领导或同事发来的周报文本往往不遵循该格式，常见如：
    - `主要工作 1. 生产安全：... 2. 智能体评测：... 3. datops建设：...`（同一行空格分隔）
    - `一、生产安全：1. 组织讨论（1）确定责任人 二、智能体评测：...`（中文数字一级 + 阿拉伯数字二级）
    - `1. Production Safety (a) Account zeroing (i) Organize discussion`（英文体系）
  - 前端纯正则难以覆盖所有自然语言写法，但内置 LLM 又过于笨重。

- **方案**：
  - 在 Java 后端新增 `TaskParseService` + `ReportParseController`，提供 `POST /api/reports/parse-tasks` 接口。
  - 前端点击「解析子任务」时保留现有前端解析作为第一梯队；只有当前端正则无法识别时，才将原始文本发送到后端做更灵活的解析。
  - 后端按以下策略由浅入深处理：
    1. 严格换行解析（兼容现有格式）；
    2. 紧凑同一行解析（空格分隔的 `1./一、` 等）；
    3. 中文混合格式（`一、1.（1）`）；
    4. 英文体系（`1. (a) (i)`）；
    5. 兜底：整段保留为根任务文本。
  - 解析结果统一返回 `{ rootText, children }`，前端通过现有 `onParseChildren` 更新任务树。

- **涉及文件（预计）**：
  - `backend/src/main/java/com/hr/backend/service/TaskParseService.java`（新增）
  - `backend/src/main/java/com/hr/backend/dto/ParsedTask.java`（新增）
  - `backend/src/main/java/com/hr/backend/controller/ReportParseController.java`（新增）
  - `src/components/weekly-report-v2/TaskTree.tsx`（新增后端 fallback 调用）
  - `backend/src/main/java/com/hr/backend/filter/JwtAuthenticationFilter.java`（确认 `/api/reports/**` 已纳入 JWT 认证）

- **主要风险**：
  - 解析规则分裂：前端、后端各有一套正则，维护不一致风险。
  - 网络延迟：前端解析失败时才调后端，存在 RTT 等待。
  - 前后端结果不一致：同一文本可能因解析策略差异产生不同结果。
  - 权限安全：新接口必须接入现有 JWT 认证，避免未授权访问。
  - ReDoS 风险：复杂正则遇到超长/特殊输入可能触发回溯，需限制输入长度并加 try-catch 兜底。
  - 过度设计：若真实复杂 case 不多，引入后端服务收益有限。

- **建议**：
  - 当前前端已通过紧凑模式覆盖 `主要工作 1. xxx 2. yyy` 等常见场景，可先继续观察真实 case。
  - 待收集到足够多的复杂样本、且前端规则确实无法覆盖时，再按本方案实施后兜底解析。

- **状态**：**暂不实施**，仅作为设计记录。


一看就知道：**不是 deadline 问题，是杨萍的部门被配成了「数据治理部」，而她正在编辑「数据测试部」的周报**。

行为日志页会多出一条：

| 时间 | 用户 | 行为 | 对象 | 详情 |

| 2026/7/10 18:05 | 杨萍 | 权限拒绝 | 20260710 数据测试部 | `deniedAction: edit`<br>`reason: dept mismatch: userDept=数据治理部 reportDept=数据测试部 ...`<br>`userDept: 数据治理部`<br>`userRole: user`<br>`userPermissions: [EDIT_REPORT, SUBMIT_REPORT, ...]` |

**场景二：用户角色被误设为 leader**

数据库状态：

| username | name | dept | role | permissions |


一看就知道：**role 被配成了 leader，leader 默认不能编辑周报**。

**场景三：currentUser 解析失败（token 问题）**

后端拿到 currentUser == null：

```
currentUser null
```

前端提示：

```
自动保存失败: 无编辑权限（已截止或不是本人）
诊断: currentUser null
```

这说明请求到后端时没拿到用户信息，排查方向变成：
- token 是否过期
- localStorage 里的 `auth-token` 是否被清空
- 请求头是否携带了 Authorization

**场景四：截止时间确实已过**

服务端时间正常，用户晚于 20:00 提交：

```
deadline passed: now=2026-07-10T20:15 ... deadline=2026-07-10T20:00 ...
```

前端提示：


一看就知道：**是 deadline 过了，不是部门或权限问题**。

**场景五：报告被管理员锁定**

```

```

**总结**

以前所有情况都显示同一句话：

> 自动保存失败：无编辑权限（已截止或不是本人）

运维只能猜。现在会直接给出「诊断」：

- `dept mismatch` → 检查用户部门配置
- `role=leader` → 检查用户角色配置
- `missing EDIT_REPORT` → 检查用户权限配置
- `deadline passed` → 检查服务端时间和 deadline
- `report locked` → 检查报告锁定状态
- `currentUser null` → 检查 token/登录状态

再配合行为日志页面的 `权限拒绝` 记录，事后也能复盘。

### 17. 修复下周计划继承时 nextPlan 被污染导致显示 JSON 字符串的问题

- **修改内容**：解决生产环境中某周「下周工作计划」继承到下一周「本周工作内容」时，直接把 JSON 字符串渲染出来的问题。根因是 `next_plan` 字段末尾被追加了非 JSON 文本（如 `[历史测试编辑]` 等），导致 `JSON.parse` 失败并回退到文本解析，把整个 JSON 字符串塞进了任务 `text`。本次改动增强了解析容错，并在后端增加写入校验，同时清洗了本地测试库中被污染的数据。
- **涉及文件**：
  - `src/components/weekly-report-v2/data.ts`
  - `backend/src/main/java/com/hr/backend/controller/ReportController.java`
  - `backend/data/hr.db`
- **具体改动**：
  - 在 `data.ts` 中新增 `extractFirstJsonArray` 辅助函数，按字符级深度遍历提取字符串中第一个完整的 JSON 数组（正确跳过字符串内的 `[`/`]`）。
  - 在 `parseNextPlan` 中增强容错：
    - 优先直接 `JSON.parse`；
    - 失败后尝试用 `extractFirstJsonArray` 截断 trailing 非 JSON 文本，再次解析；
    - 仍失败才回退到 `parsePlanToTree`。
  - 在 `ReportController.java` 的 `saveReport` 中增加 `nextPlan` 格式校验：
    - 如果 `nextPlan` 非空且以 `[` 开头，必须能被 Jackson 解析为数组；
    - 否则返回 `code: INVALID_NEXT_PLAN`，拒绝保存异常数据入数据库。
  - 用脚本扫描并修复本地 `backend/data/hr.db` 中被污染的 `next_plan`：
    - 定位到 `20260522 / 项目管理` 的 `next_plan` 末尾被追加了 `[历史测试编辑]\n[历史最终测试]\n[cleanup history test]`；
    - 提取合法 JSON 数组部分并写回数据库，共修复 1 条记录。
- **验证**：
  - 后端 `mvn package -DskipTests` 通过。
  - 前端 `NODE_OPTIONS=--max-old-space-size=8192 npm run build` 通过（5m 17s）。
- **注意事项**：
  - 本地 `hr.db` 修复后，重新打包部署时**不要覆盖生产环境 `data/` 目录**，否则生产真实数据会丢失。
  - 生产环境若存在同样被污染的 `next_plan`，需要单独在生产库执行清洗或依赖新的解析容错自动修复显示。

#### 问题定位过程

在修复前，先在本地 `backend/data/hr.db` 里找到了一个活生生的例子：

> 在本地 `backend/data/hr.db` 里，`20260522 / 项目管理` 这条记录的 `next_plan` 字段末尾被追加了一些非 JSON 文本：
>
> ```json
> [{"id":"1780984877088-147208","text":"2026年数据部立项工作：", ... }]
> [历史测试编辑]
> [历史最终测试]
> [cleanup history test]
> ```
>
> 就是这样导致 `JSON.parse` 失败：
>
> ```
> Extra data: line 2 column 1 (char 784)
> ```
>
> 当 `parseNextPlan` 发现 `JSON.parse` 失败后，会回退到 `parsePlanToTree`。而 `parsePlanToTree` 是文本解析器，它会把整个 `next_plan` 字符串当成一个普通文本块，生成一个任务节点，该任务的 `text` 字段就是那段完整的 JSON 字符串。于是下一周继承过来的 `content` 里就多了一个 `text` 为 JSON 字符串的任务，前端 TaskTree 就直接把这段 JSON 当作文本显示出来了。

#### 测试验证

修复后，用 `20260612 / 智能平台部` 的正常 `next_plan` 模拟污染场景（在合法 JSON 末尾追加 `[历史测试编辑]` 等非 JSON 文本）进行对比测试：

| 逻辑 | 解析结果 |
|------|---------|
| 旧逻辑 | 1 个任务，`text` 为完整 JSON 字符串（1622 字符） |
| 新逻辑 | 4 个任务，与原始干净数据解析结果一致 |

测试结果表明，新的容错解析可以正确忽略 trailing 非 JSON 污染文本，还原出真实的任务列表。
